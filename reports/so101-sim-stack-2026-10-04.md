# The SO-101 simulation stack, as actually built

Built 2026-10-04 on the Windows laptop, documented here 2026-10-11. This is the
record of a working simulation-first setup for the SO-101 arm: what is installed,
what each layer does, what was deliberately left out, and the two Windows-specific
failures that were hit and fixed. It is an infrastructure document, not research.
The source of truth is the machine itself at
`C:\Users\anshu\Desktop\Stanford_acads\Quarter_1\Robotics`, with `README.md` and
`notes/00-stack-map.md` in that folder; this report is the portal's copy.

## 1. Why this exists

The measurement-rig thesis needs a body to measure policies on. The SO-101 is the
cheapest credible one, and a simulation of it costs nothing per rollout, runs
without the physical arm present, and can be rebuilt on any machine from the files
listed here. Everything below was chosen so that **one environment serves both the
simulation and the physical arm when it arrives** — no second setup, no porting
step.

The deliberate shape of the build: simulation first, hardware second, and every
package in it justified against a job. Packages that would be reasonable to install
and were not are listed in section 5, with the reason.

## 2. The layers

| Layer | Package | Job |
|---|---|---|
| Physics | `mujoco` 3.14.0 | Integrates rigid-body dynamics and contact. `mj_step(model, data)`. |
| Robot description | `mujoco_menagerie/robotstudio_so101` | MJCF XML: links, inertias, joint limits, meshes, actuators. |
| Task interface | `gymnasium` 1.3.0 | `reset()` / `step(action)` → obs, reward, done. The universal socket. |
| Inverse kinematics | `mink` 1.3.0 | "Move the gripper to (x, y, z)" → joint velocities, via a QP each timestep. |
| Deep learning | `torch` 2.11.0+cu128 | Autodiff and GPU. RTX 3050 Ti, 4 GB VRAM. |
| Robot learning | `lerobot` 0.6.1 | Dataset format, policies (ACT, Diffusion, SmolVLA, pi0), train and eval scripts, SO-101 drivers. |
| Video | `ffmpeg` 7.1.1 + `torchcodec` 0.11.1 | Datasets store camera frames as mp4 and decode straight to tensors. |
| Visualisation | `rerun-sdk` 0.33.1 | Scrub a timeline of camera, joint traces and actions together. |
| Experiment tracking | `wandb` | Training curves. Optional. |

Environment: `C:\Users\anshu\miniforge3\envs\lerobot`, conda, Python 3.12.14.
The model zoo is a 2.3 GB git clone of DeepMind's `mujoco_menagerie`.

### The distinction the whole API rests on

`mjModel` is constant — it *is* the robot, built once from XML. `mjData` is mutable
— `qpos`, `qvel`, `ctrl`, contacts — and is "the current moment". Every MuJoCo call
takes both. Confusing the two is the most common way to write simulation code that
silently does nothing.

## 3. The arm, as MuJoCo sees it

Six actuated joints, all position-controlled, which is the same control mode as the
real STS3215 servos:

| idx | joint | range (rad) |
|---|---|---|
| 0 | shoulder_pan | −1.92 … +1.92 |
| 1 | shoulder_lift | −1.75 … +1.75 |
| 2 | elbow_flex | −1.69 … +1.69 |
| 3 | wrist_flex | −1.66 … +1.66 |
| 4 | wrist_roll | −2.74 … +2.84 |
| 5 | gripper | −0.17 … +1.75 |

Bodies: `world, base, shoulder, upper_arm, lower_arm, wrist, gripper, camera_mount,
moving_jaw_so101_v1, box`.

Two things on that list matter more than they look. `camera_mount` is already in the
model, which is where observation images come from without any further rigging.
And `scene_box.xml` adds a free-floating box, which takes the state to `nq = 13`
(six arm joints plus seven for the box's free joint: three position, four
quaternion) and `nv = 12` — the quaternion is the reason those two numbers differ,
and it is the standard place this arithmetic goes wrong.

## 4. The three scripts

Numbered so the order is the lesson, in `sim/scripts/`:

- **`00_verify_install.py`** (103 lines) — checks each layer independently, so a
  failure names *which* layer broke rather than surfacing a generic import error.
  This is the one to run first and to re-run whenever something mysterious breaks.
- **`01_hello_so101.py`** (81 lines) — the smallest possible MuJoCo program: load
  the MJCF into an `mjModel`, create the matching `mjData`, step physics in real
  time and draw it. The arm flops under gravity, because nothing is holding it up
  yet. That is the correct result.
- **`02_position_control.py`** (72 lines) — writes a desired joint angle into
  `data.ctrl[i]` and lets MuJoCo's internal PD controller apply torque proportional
  to (target − current) minus a damping term. The arm does not snap to the target:
  it accelerates, overshoots slightly and settles. That lag exists on the hardware
  too, and ignoring it is how people write control code that oscillates.

`START-ROBOTICS.cmd` opens a terminal with the environment already active, but the
environment is configured to work without activation as well, so VS Code's run
button and Jupyter kernels work unaided. The reason that is true is in section 6.

## 5. Deliberately not installed

- **ROS 2** — a different ecosystem; LeRobot does not need it. (ROS 2 does exist on
  this laptop, in the CS237A devcontainer, which is a separate stack entirely.)
- **Isaac Sim / Isaac Lab** — NVIDIA GPU simulation; 4 GB of VRAM is not enough, and
  the conceptual load is higher than this stage needs.
- **MJX**, GPU-parallel MuJoCo via JAX — for massively parallel RL. Later.
- **feetech-servo-sdk** — only needed when the physical arm arrives, at which point
  it is `pip install "lerobot[feetech]"`.

## 6. The two Windows failures, and the fixes

Both were hit during the build. Both will recur on a fresh machine, which is why
they are written down.

**1. ffmpeg must stay pinned at 7.1.1.** conda-forge now defaults to 9.x, but
torchcodec 0.11.1 only ships loaders for ffmpeg 4 through 8. With a 9.x ffmpeg,
video decoding in `LeRobotDataset` dies with `Could not load libtorchcodec`. After
any `conda update`, re-pin:

```
conda install -p <env> ffmpeg=7.1.1 -c conda-forge
```

**2. `Lib\site-packages\zzz_conda_dll_dirs.pth`.** This file puts `<env>\Library\bin`
on `PATH` and calls `os.add_dll_directory` at interpreter startup. Without it,
native DLLs — ffmpeg, MKL — are only findable *after* `conda activate`, which
silently breaks IDE run buttons and Jupyter kernels while leaving the terminal
working. The failure mode is confusing precisely because the terminal is fine.

## 7. Why native Windows rather than WSL2

Three reasons, in the order they decided it:

1. The MuJoCo viewer gets real GPU OpenGL rather than WSLg's software path.
2. CUDA works directly.
3. The physical SO-101's USB-serial adapter is a native COM port. Getting USB into
   WSL2 needs `usbipd` and breaks on every reconnect. One environment serves both
   the simulation and the real arm.

The third reason is the load-bearing one, and it is a bet on the hardware arriving.

## 8. What this does not yet do

No policy has been trained or evaluated on this stack. `datasets/` is empty — no
LeRobotDataset has been recorded. There is no Gymnasium environment wrapping the
arm yet, no evaluation harness, and no comparison of ACT, SmolVLA or a zero-shot
frontier model, all of which the measurement-rig thesis needs and none of which
exists here today. What exists is a verified physics layer, a correct robot
description, a working viewer, position control, and an environment that will not
have to be rebuilt to do any of the above.
